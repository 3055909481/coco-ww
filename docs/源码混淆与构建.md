# 源码混淆与 release 构建

release 里分发的不是明文源码，而是**AST 混淆 + 编译后的 `.pyc`**。本文说明构建方式、防护范围和注意事项。

## 一句话原理

1. `src/`、`pyappify/`、`config.py`、`main.py` 等自有源码先经过 AST 混淆（去注释/docstring、编码长字符串常量、AST 重排；**不重命名任何标识符**，原因见下方"防护范围"）；
2. 用与发布包运行环境一致的 **Python 3.12** 编译成 hash-based 的 sourceless `.pyc`（不放 `__pycache__`，直接替代 `.py`）；
3. 输出目录里**没有项目自身的明文 `.py`**；
4. 内置角色的原始源码（"查看/编辑内置代码"功能要用）在混淆前单独加密存进 `src/_builtin_sources.dat`，运行时按需解密；
5. 在线更新清单基于混淆产物生成，清单里的路径是 `.pyc`，`commit` 指向 `obfuscated` 分支——用户更新时下载到的也是混淆产物，不会把源码带回来。

## 构建命令

```powershell
# 需要本机有 Python 3.12（py -3.12）；发布包自带 3.12，字节码必须与它同版本
py -3.12 -m pip install -r requirements.txt   # 仅为验证用；构建本身只用标准库
python -X utf8 tools/obfuscate_build.py --out build\release

# 用其它 3.12 解释器
python -X utf8 tools/obfuscate_build.py --out build\release --python "C:\Python312\python.exe"
```

构建产物在 `build/release/`，结构与原仓库一致，但 `src/`、`pyappify/` 下全是 `.pyc`，另多出：
- `src/_builtin_sources.dat` — 加密的内置角色源码
- `version.txt` — 明文版本号（更新器与清单读取用，版本不是敏感信息）

启动脚本里的入口已自动改成 `main.pyc` / `main_debug.pyc`。

## 自动发布（GitHub Actions，含整包）

`push` 到 `main` 且 `config.py` 的版本号变化时，`.github/workflows/release.yml` 会（**runner 是 `windows-latest`**，因为整包要装 `pywin32`/`comtypes`/`pycaw` 等 Windows 专属依赖）：
1. 用 Go 编译独立启动器 `coco-ww.exe`（图标取自 `icons/icon.ico`，带 `requireAdministrator` manifest）；
2. 构建混淆产物到 `build/release/`，并把启动器放进产物、`启动 coco-ww.bat` 改为转发到它；
3. 把产物推到 `obfuscated` 分支（每次整棵覆盖，force push）；
4. 用混淆产物 + 干净的 Python 3.12 运行环境打整包 `coco-ww-vX.Y.Z.zip`（约 313 MB，自带 `python/pythonw.exe` 和全部依赖）；
5. 基于产物生成 `update-manifest.json`（`commit` 指向 `obfuscated` 分支，`version` 从 `version.txt` 读）；
6. 创建 Release，同时挂上整包 zip 和清单。

用户下载整包解压到纯英文路径，双击 `coco-ww.exe` 即可运行；在线更新走清单，下载路径是 `raw.githubusercontent.com/<仓库>/<obfuscated 提交号>/<路径>`，拿到的都是 `.pyc`。

### 启动器（`launcher/`）

Go 写的独立 exe，负责：UAC 提权（manifest 声明 + 代码兜底）、单实例检测（命名 Mutex）、路径含中文/依赖缺失/未提权的弹窗提示、GitHub 更新检查（读 raw 域名的 `version.txt`，不计入 API 配额、不会被限流；有新版本提示打开下载页，不自行替换文件）、最后拉起 `python\pythonw.exe -X utf8 main.pyc`。图标和版本信息由 `go-winres` 在 CI 里现场注入。

程序内的更新检测（`pyappify`）同样优先走 GitHub API，但在 API 被限流（HTTP 403/429）时自动降级：从 raw 域名读 `version.txt` 拿最新版号，清单走 `github.com/releases/download/`（二者都不计 API 配额）。这样国内共享 IP 被限流时也能正常检查更新，不再误报失败。降级只覆盖"检查更新/更新到最新版"，历史版本列表在限流时不可选——不影响常规使用。

本地编译（改了源码想验证时）：
```powershell
cd launcher
go test ./...                       # 注意：先跑测试，生成 syso 后测试 exe 会要求提权
go-winres simply --icon ../icons/icon.ico --manifest gui --admin --arch amd64 --out rsrc --no-suffix --file-version 1.0.8.0 --product-version 1.0.8.0
mv rsrc rsrc.syso
go build -trimpath -ldflags "-H=windowsgui -s -w -X main.repo=3055909481/coco-ww" -o coco-ww.exe .
```

本地也可手动打整包（同样需 Windows + 3.12，会下载安装全部依赖，较慢）：
```powershell
python -X utf8 tools/pack_release.py --obf-dir build\release
```

> **Fork 后必改**：`pyappify/__init__.py` 的 `REPO` 和 `launcher/main.go` 里 `repo` 的默认值（会被 CI 用 `-X main.repo` 覆盖）都要改成你的仓库 `owner/repo`，否则更新器/启动器会去上游取信息。

## 测试

```powershell
python -X utf8 tests\test_obfuscation.py      # 混淆链路 16 项测试
python -X utf8 tests\test_online_update.py    # 原有在线更新测试（回归）
```

测试会验证：AST 变换语义等价（含 `global/nonlocal`、关键字参数、字符串编码）、**所有标识符零改名**、历史两次 NameError 场景不再复发、全部真实源码可编译、加密 round-trip、产物无明文源码与 `_obfN` 残留、`.pyc` 可加载且 `co_filename` 正确、清单 hash 正确、启动脚本已改写。

## 防护范围与限制（务必了解）

- **这是源码混淆，不是密码学加密。** 目的是让人打开 release 目录时看不到核心逻辑、提高逆向门槛；`.pyc` 可被反编译，密钥也在程序里，无法阻止下定决心的攻击者。
- **只混淆项目自有源码**：`src/`、`pyappify/`、`config.py`、`main.py`、`main_debug.py`。`ok/` 是第三方开源框架（ok-script），按原样分发；`configs/` 是用户数据与内置队伍代码，必须保持可编辑，不混淆。
- **不重命名任何标识符（变量、参数、函数、类、属性）**。这是刻意的永久决策：曾做过局部变量重命名，但连续两次导致实机 `NameError`（v1.0.6 的 `_obf62`、v1.0.7 的 `_obf70`），根因是推导式/lambda/闭包的作用域规则极其微妙，手写 AST 跟踪无法穷尽。而 pyc 的 `co_varnames` 本来就明文保存变量名，反编译器可直接读出，重命名的防护收益几乎为零。测试 `test_no_identifier_is_ever_renamed` 对全部源码强制校验"零改名"，防止有人加回来。
- **`.pyc` 与 Python 版本强绑定**：必须用 3.12 编译；换 Python 版本要重新构建整包，并更新 `requirements.txt`（更新器会提示用户下载整包）。
- **内置源码加密是可解的**：因为"查看/编辑内置代码"功能本来就要把源码显示给用户，密文与解密逻辑都在客户端，这是设计使然，不是漏洞。
