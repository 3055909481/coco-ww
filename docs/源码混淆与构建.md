# 源码混淆与 release 构建

release 里分发的不是明文源码，而是**AST 混淆 + 编译后的 `.pyc`**。本文说明构建方式、防护范围和注意事项。

## 一句话原理

1. `src/`、`pyappify/`、`config.py`、`main.py` 等自有源码先经过 AST 混淆（去注释/docstring、重命名局部变量、编码长字符串常量）；
2. 用与发布包运行环境一致的 **Python 3.12** 编译成 hash-based 的 sourceless `.pyc`（不放 `__pycache__`，直接替代 `.py`）；
3. 输出目录里**没有项目自身的明文 `.py`**；
4. 内置角色的原始源码（"查看/编辑内置代码"功能要用）在混淆前单独加密存进 `src/_builtin_sources.dat`，运行时按需解密；
5. 在线更新清单基于混淆产物生成，清单里的路径是 `.pyc`，`commit` 指向 `obfuscated` 分支——用户更新时下载到的也是混淆产物，不会把源码带回来。

## 构建命令

```powershell
# 需要本机有 Python 3.12（py -3.12）；发布包自带 3.12，字节码必须与它同版本
py -3.12 -m pip install -r requirements.txt   # 仅为验证用；构建本身只用标准库
python -X utf8 tools/obfuscate_build.py --out build\release

# 用其它 3.12 解释器
python -X utf8 tools/obfuscate_build.py --out build\release --python "C:\Python312\python.exe"
```

构建产物在 `build/release/`，结构与原仓库一致，但 `src/`、`pyappify/` 下全是 `.pyc`，另多出：
- `src/_builtin_sources.dat` — 加密的内置角色源码
- `version.txt` — 明文版本号（更新器与清单读取用，版本不是敏感信息）

启动脚本里的入口已自动改成 `main.pyc` / `main_debug.pyc`。

## 自动发布（GitHub Actions，含整包）

`push` 到 `main` 且 `config.py` 的版本号变化时，`.github/workflows/release.yml` 会（**runner 是 `windows-latest`**，因为整包要装 `pywin32`/`comtypes`/`pycaw` 等 Windows 专属依赖）：
1. 构建混淆产物到 `build/release/`；
2. 把产物推到 `obfuscated` 分支（每次整棵覆盖，force push）；
3. 用混淆产物 + 干净的 Python 3.12 运行环境打整包 `coco-ww-vX.Y.Z.zip`（约 313 MB，自带 `python/pythonw.exe` 和全部依赖）；
4. 基于产物生成 `update-manifest.json`（`commit` 指向 `obfuscated` 分支，`version` 从 `version.txt` 读）；
5. 创建 Release，同时挂上整包 zip 和清单。

用户下载整包解压到纯英文路径即可运行（`启动 coco-ww.bat`）；在线更新则走清单，下载路径是 `raw.githubusercontent.com/<仓库>/<obfuscated 提交号>/<路径>`，拿到的都是 `.pyc`。

本地也可手动打整包（同样需 Windows + 3.12，会下载安装全部依赖，较慢）：
```powershell
python -X utf8 tools/pack_release.py --obf-dir build\release
```

> **Fork 后必改**：`pyappify/__init__.py` 里的 `REPO = "wk321425/coco-ww"` 要改成你的仓库（`owner/repo`），否则更新器会去上游仓库取清单。

## 测试

```powershell
python -X utf8 tests\test_obfuscation.py      # 混淆链路 16 项测试
python -X utf8 tests\test_online_update.py    # 原有在线更新测试（回归）
```

测试会验证：AST 变换语义等价（含 `global/nonlocal`、关键字参数、字符串编码）、全部真实源码可编译、加密 round-trip、产物无明文源码、`.pyc` 可加载且 `co_filename` 正确、清单 hash 正确、启动脚本已改写。

## 防护范围与限制（务必了解）

- **这是源码混淆，不是密码学加密。** 目的是让人打开 release 目录时看不到核心逻辑、提高逆向门槛；`.pyc` 可被反编译，密钥也在程序里，无法阻止下定决心的攻击者。
- **只混淆项目自有源码**：`src/`、`pyappify/`、`config.py`、`main.py`、`main_debug.py`。`ok/` 是第三方开源框架（ok-script），按原样分发；`configs/` 是用户数据与内置队伍代码，必须保持可编辑，不混淆。
- **参数名不重命名**：外部可能用关键字参数调用（如 `RecentLogs(capacity=3)`），改了会破坏调用方。只重命名函数体内的纯局部变量。
- **`nonlocal` 所在模块跳过局部变量重命名**：跨作用域绑定容易出错，正确性优先。
- **`.pyc` 与 Python 版本强绑定**：必须用 3.12 编译；换 Python 版本要重新构建整包，并更新 `requirements.txt`（更新器会提示用户下载整包）。
- **内置源码加密是可解的**：因为"查看/编辑内置代码"功能本来就要把源码显示给用户，密文与解密逻辑都在客户端，这是设计使然，不是漏洞。
